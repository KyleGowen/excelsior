# Independent frontend modules (M5)

`index.ts` is the source entry point for Card Database, Deck Builder and Collection. Each existing route page is a thin adapter rendering this same implementation. Controllers own requests, query state, drafts and mutations; views receive display state/capabilities and callbacks. Detail actions and lazy panels keep their own small controllers under the declared host. No duplicate page implementation or embedded full SPA is used.

## Required host contract

Provide `QueryClientProvider`, `LayoutModeProvider`, shared `styles/appStyles`, and `ModuleHostProvider` with a stable `ModuleHost`:

- `api`: one `createModuleApi(transport)` client, or typed fictional operations. M2 transport retains origin/prefix validation, cookies/player headers, bounded renewal and server-secret protection. Binding a host never changes global API functions.
- `identity`: user/null plus explicit Guest/admin capabilities supplied by the host. Modules do not authenticate, bootstrap a Guest session or mount AuthProvider.
- `onOpenDeck`, `onBack`, `onHome`: callbacks; the host chooses URLs. Deck Builder takes `deckId` and optional `readonly` (default false). Standalone fixtures should explicitly start readonly.
- Optional `backLabel`, neutral detail-history navigation/state port and desktop/mobile chrome slots. Without history, detail closes locally; without chrome, Deck Builder uses one column.

Use one QueryClient per API/data environment and identity lifecycle. Modules in that same host may share catalog/collection/deck keys. Dispose or clear that client's queries when switching API origin or authenticated player; do not reuse cached account data across hosts/players. Identity capabilities are UI inputs, never server authorization. Public reads do not grant ownership; actual mutations still use existing backend ownership and transport policy.

Card Database browses independently of Deck/Collection pages. Opening its detail actions may request collection data; only opening Add to Deck requests available decks. Deck Builder requests its own catalogs directly. Collection uses catalog primitives and its supplied collection adapter, with the existing browser-local Guest store. These are declared feature dependencies, not another page mount.

## Lifecycle and fixture harness

`/module-harness.html` on a verified development server mounts no AuthProvider, router or AppShell. Its host reads the current local session/config without creating a session, supplies callbacks, and offers each module alone, together and unmounted. It displays Guest/account mode and starts decks read-only. Reload after changing the session in another tab. Use a named fictional/local deck; never substitute a real production account for a fixture. Close a module modal before using host controls covered by its backdrop. React fixture tests additionally unmount while a detail is open and verify disposal.

Catalog/deck reads consume cancellation signals. Detail/Guest collection listeners and debounced timers detach on unmount; session bootstrap ignores completion after disposal, and the Vite entry disposes its root/cache on hot reload. Module failures show retry without requiring a full host reload. Successful tests do not imply Kyle's acceptance.

## Current delivery limits

This is a source-level interface, not a distributable package. Existing global CSS/layout classes, image CDN initialization and browser-local Guest collection storage remain shared. Host theme/container/overlay/asset isolation is M6; package exports and removal of backend source imports are M7. M4 simulation/import/export/Collection domain contracts remain explicitly open. Do not claim native-host containment or complete backend-domain migration from this structural extraction.

Fixtures and named examples live in `frontend/src/stories/IndependentModules.stories.tsx` and ordinary Screen stories. Dedicated component tests: `npx jest --config tests/config/jest.frontend-modules.config.js --runInBand`; they are mocked jsdom cases, not browser tests. Shared live cases: `tests/browser/milestone5-modules.mjs`, using `tests/helpers/browserEvidence.mjs`. CI runs the dedicated suite once, after unit shard 1, against the locked frontend runtime.

## M6 first slice: host-owned overlay placement

`ModuleHost.overlays` accepts `{ root: HTMLElement, position?: 'absolute' | 'fixed', modal?: boolean }`. Supply a mounted host-owned root; absolute is the configured-root default, and modal defaults true. The host controls the containing block and stacking. Example: a relative module surface contains a root with `position:absolute; inset:0; z-index:1000; pointer-events:none`, while its `.slideout` children accept pointer events. Keep the root alive for its panels; give each independent host its own root. Omit `overlays` to retain Excelsior's inline, existing positioning behavior. The provider changes no body/document attributes or scroll styles.

Configured panels portal into that root, fit its available bounds, restore their connected trigger, and handle Escape only for their focused panel. Modal panels wrap Tab/Shift-Tab inside enabled visible controls; `modal:false` declares a nonmodal dialog and leaves Tab movement to the host/browser. Keep the existing `closeOnEscape:false` parent/child contract where appropriate. Root/config changes dispose the old listener and portal; unmount removes owned content, leaving the host root itself intact. This placement contract does not replace server authorization or perform authentication.

The development harness offers **Use host overlay root**; its controls stay outside the panel surface so Unmount can demonstrate open-panel cleanup. Named examples cover a module detail in its host root, nonmodal panels and independent roots. Live checks: `tests/browser/milestone6-overlays.mjs`; fictional component checks use the existing dedicated module runner. Alternative theme/style containment, container-responsive detection, brand/icon/auth/action slots and the complete native-host contract are still M6 backlog. The current harness still imports global Excelsior styles; it is not evidence of CSS isolation or an exact LRG visual match.

## M6 second slice: container-owned layout context

Set `ModuleHost.layout = { mode: 'container', mobileMaxWidth?: number }` to measure the provider's own wrapper instead of the viewport. The positive finite threshold defaults900px; ResizeObserver updates mode without a window resize. The wrapper supplies `useLayoutMode()` and its own mobile/desktop classes, bounded width and a relative containing block. Zero-width/hidden surfaces start mobile until measured. Each instance owns its measurement and local desktop preference; neither device storage nor document layout attributes are changed. Disposal disconnects the observer and ignores queued callbacks. Without ResizeObserver, the limited fallback measures on mount and window resize only; arbitrary container changes then require host resize events. That fallback has component evidence only.

Omit `layout` for the unchanged Excelsior viewport provider and DOM shape. Configure at mount: turning container mode on/off changes the wrapper and remounts its module children, so a real host must not toggle it over an unsaved draft without its normal discard/save policy. Changing the threshold within container mode does not remount. The development harness uses read-only fixtures and offers **Use container layout** plus **Host container width**. Enable its host overlay root too when testing container-bounded panels. Place host roots inside the wrapper to inherit its layout classes and positioning; a root elsewhere must be styled by its owner.

The harness keeps viewport classes local instead of writing them to the document. Configured mobile Draw Hand stays within its root; configured narrow-host pagination wraps rather than widening Collection. Ordinary Excelsior pagination/draw defaults are unchanged. Named examples include NarrowContainerOnDesktop, ResizableContainer and NarrowHostPagination. `tests/browser/milestone6-containers.mjs` checks container-only resizing, keyboard/detail placement, read-only deck draw/export, unfiltered Collection pagination and cleanup. Dedicated mocked component tests prove multiple widths, threshold updates, preference isolation and observer disposal; they are not live browser tests.

This is responsive-context preparation, not full native style containment. Existing global resets, inherited token variables, ancestor selector collisions, viewport media queries, overlay roots outside the boundary, theme/brand/icon/auth/action slots and actual LRG assets remain open. No exact LRG visual match or CSS-leak-free embedding is claimed.


## M6 third slice: per-instance appearance

`ModuleHost.appearance` optionally accepts `{ tokens, colorScheme }`. `tokens` is a partial map of reviewed visual CSS custom properties (`ModuleThemeToken`): the current color, font, line-height, spacing, radius and shadow tokens in `styles/tokens.css`. Layout widths, z-index and motion are intentionally outside this visual port. Unsupported keys, non-object maps, empty/non-string/oversized values and unsupported color schemes throw before rendering. Values are trusted host CSS configuration, not untrusted catalog content; supply valid CSS and review your host's accessibility. Omitted tokens inherit from the containing host. A partial preset is not a full reset, and nested hosts inherit any ancestor variables they do not override.

The opt-in `ModuleAppearanceBoundary` sets variables and font/color/background only on its own wrapper. It never changes document/body attributes, storage or global stylesheets. Explicit font properties make host typography apply even when the page body already specifies a font. `colorScheme: 'light' | 'dark'` controls native form controls locally; it does not add a site theme switch. Ordinary Excelsior omits appearance and retains its DOM/defaults. Configure boundary presence at mount: adding/removing `appearance` remounts children, so obey the host's unsaved-draft policy. Keep `appearance: {}` to reset overrides while preserving the boundary; updating tokens/color scheme inside it preserves module state.

A portal root inside the wrapper inherits its appearance; one outside it requires the host's own equivalent styling. An external root does not acquire scoped tokens merely because the overlay configuration points to it. Container layout and appearance may be combined; each instance owns its supplied overrides. This is a source interface rather than a bundled native-host SDK.

The development harness adds **Host appearance** with Excelsior defaults, Paper fixture and High contrast fixture. These fictional presets demonstrate typography, colors, spacing and native-control changes. They are not certified accessibility palettes, complete light-theme coverage, an LRG reskin or a replacement for host assets. Named examples: PaperHostAppearance (including a detail overlay), ContrastHostAppearance and IndependentHostAppearances. Shared live tests are in `tests/browser/milestone6-appearance.mjs`; jsdom instance/draft/portal checks stay in the dedicated frontend-module suite. Global resets, ancestor CSS collisions, fixed colors, viewport media queries, rem units and third-party token aliases still prevent a CSS-leak-free claim. Theme configurability alone does not fulfill the remaining brand/icon/auth/action or full M6 contracts.


## M6 fourth slice: host-owned card-detail actions

`ModuleHost.cardActions` optionally supplies `{ render, requestAuthentication }`. `render(context)` replaces only the card-detail action area in Database, Collection and Deck Builder. The context carries source, the currently selected catalog card/type, Guest state, a close callback, optional Deck `{ id, readOnly }`, and a sign-in request callback only when configured. Returning `null` intentionally suppresses this area. Omit the configuration to preserve Excelsior defaults: disabled Guest deck-add plus Collection action, Collection quantity stepper, and no extra read-only Deck action row. Existing printing/pre-placement controls and grid quantity/edit controls remain governed by their existing modules.

Render functions are trusted host presentation callbacks, called during React rendering; keep them pure and return nodes or host components. They must not call hooks directly, navigate, authenticate or mutate data while rendering. A host may supply its own labels/icons in this slot. No API client, credential, mutation helper or player object is passed to it. UI Guest/read-only values are presentation context, never server permission grants. Any host action that writes still needs the authenticated transport, server ownership rules and the host's explicit mutation policy.

`requestAuthentication` receives only source, catalog type/card ID and optional deck ID. It is called on an explicit user action, never automatically on opening a detail. The host chooses its sign-in UI and safe return/discard policy; modules do not assume URLs, route prefixes, account migrations or perform auth themselves. Context close delegates to the existing detail-history/focus/portal lifecycle. Authentication completion and identity changes still require the existing host-specific identity/QueryClient lifecycle; this callback does not implement them.

The development harness checkbox **Use host card actions** renders fictional action/sign-in/close buttons. Action and sign-in buttons only display a host receipt; they make no HTTP write, login or navigation. Switching this configuration preserves mounted detail/search state. Named stories exercise Guest/account Database actions, Collection and read-only Deck actions. Shared live scenarios: `tests/browser/milestone6-actions.mjs`. Fixtures cover desktop/mobile, source/type/card callbacks, Enter activation, focus return, portal cleanup and preserved defaults. Dedicated component tests additionally cover `null`, renderer changes and two independent Guest/account hosts. See [future host integration checklist](../../../docs/current/FRONTEND_HOST_CHECKLIST.md) for remaining inputs and limits. Save feedback, broader feature slots, brand/core icon ports, nested host-route testing and complete CSS containment remain open M6 work.

## Host brand and decorative icon controls

A host may supply `chrome.brand` as its own accessible React node and `icons: { render(context) }` for decorative UI controls. The callback receives the typed semantic `UIIconName`, `filled` state and optional caller `className`; no player, API, credential or mutation access is provided. Return `undefined` for the existing SVG, `null` to hide decoration, or an inert node. Render callbacks are pure: no direct hooks, requests, navigation or effects. The wrapper preserves caller class/style and hides decoration from assistive technology; keep replacement nodes noninteractive/nonfocusable and sized for one-em controls. It cannot change surrounding labels or action permissions. Card images, printed game/stat symbols and Google's identity asset stay separate; their delivery belongs to M7.

The brand is host content outside the module appearance boundary, styled/named by the host. There is no built-in replacement brand, asset upload, logo lookup or route change. Each provider owns its icon configuration; context follows portals even into external overlay roots. Updating/omitting it preserves mounted module/detail/search state and restores SVG defaults. No document/global renderer, stylesheet, storage or real host is changed.

The development harness **Use host brand and icons** uses a fictional diamond and label. Named stories: HostBrandIcons, HostCollectionIcons, HostDeckIcons and IndependentHostIcons. The seven new dedicated component cases cover sources, fallback/null/class/style/filled state, updates, separate hosts and portal disposal. Shared live cases reuse `tests/browser/milestone6-actions.mjs` with `hostIcons:true` and add `tests/browser/milestone6-icons.mjs` for open-detail update/focus/unmount behavior. These fixtures do not establish real host asset accessibility/licensing, account lifecycle, production customization or CSS isolation. Save feedback, nested host route evidence and broad CSS containment remain M6 backlog.

### Save-feedback preparation

`saveFeedback.render` is an optional pure presentation slot with status/message/newer-edits context only. No record identifiers, identity, API or mutation callbacks are exposed. Omitted/undefined retains default results; null hides the configured feedback. Read-only modules gain no Save action. Existing multi-request persistence and failure semantics remain unchanged. The development harness supports real local, delayed and intentionally rejected save modes; injected rejection is not evidence of a backend outage. See [contract](saveFeedback.md). Nested host routes/full CSS and retained M4 domain work remain open.
