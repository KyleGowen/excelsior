# Production target, safe subset, and evidence limits

## Establish revision before the browser

Use the existing [Ship workflow](../../ship/SKILL.md) for the exact candidate/main release evidence. A verification-only request does not trigger Ship's commit/push flow. Read the supplied release SHA/run evidence; if needed use read-only GitHub run metadata and logs. The deployed run must be terminal success, `headSha` must match the expected full SHA, and actual required job/test steps must have run. Never dispatch a new run just to obtain evidence.

After deployment succeeds, get cache-bypassed health using the same contract as Ship. This helper is read-only but is still a **live production request**; do not run it during a task that forbids production testing:

```bash
node scripts/browser-test-target.mjs \
  --mode production --frontend https://excelsior.cards --api https://excelsior.cards \
  --expected-revision <full-deployed-sha> --expected-migration <expected-version> \
  --source-root <source-checkout> > <private-evidence-dir>/target.json
```

The helper sends a nonce plus no-cache headers, checks app/database OK and exact SHA/migration, and stores only sanitized health fields. It does not prove CI passed or identify the frontend revision independently; combine it with exact deployment evidence, correct origin and fresh browser navigation. Source checkout revision/fingerprint may differ from deployment; report both explicitly. For skill/helper validation without production contact, append `--dry-run`: it performs local Git reads only and returns `verified: false`, which the browser runner rejects.

Do not poll production before the intended deployment succeeds. A stale already-open tab may contain an older lazy bundle; fresh test-owned navigation plus image/control checks is needed. If frontend/API evidence disagrees, keep the test blocked and investigate the asset/deployment evidence. Do not classify every loading error as an auth failure or mutate infrastructure to recover browser smoke.

## Select only current read-only fixtures

M1's successful production automation used a Guest session. Opening a new tab can reuse an authenticated session; confirm Guest visually before any capture of account-specific content. If the browser is signed into a real account, select an available isolated Guest surface or report blocked. Do not log out or clear storage without authorization.

- **Home:** Welcome heading, normal navigation, contextual Log In/Create Account/Google controls. Opening a menu is supported; actual account creation or OAuth submission is outside this subset.
- **Database:** navigation, selected public card search/detail, complete artwork with positive natural dimensions. M1 used Lancelot; resolve its current result and art. For the extracted database case set `skipEmptySearch: true` to stay within M1's demonstrated production subcases. Empty-search production behavior remains unverified until explicitly selected and run.
- **Read-only Deck Builder:** choose a currently accessible public deck from Home/Community or an explicitly supplied known public route. Confirm the route exists, deck metadata and independently expected export metrics before running. Supply same-origin `deckUrl` ending in `?readonly=true`, `expectedDrawCount` and selected `expectedExport` fields. M1 found no Save/name editor, drew/redrew eight cards and inspected export. Do not hard-code old deck/user IDs or current sample counts in a skill. Random hand composition need not match; fixture-defined count/rules must.
- **Guest Collection:** actual heading **My Collection**, “Stored on this device,” Owned only, and fixture-appropriate empty/content state. Do not increase/decrease quantities. An existing Guest collection must stay intact; choose `expectEmpty: true` only when its emptiness is independently established. M1 checked an empty collection.
- **Retired Supporter:** `/supporter` redirected Home, no text/links; old status API returned 404 separately. A generic Express SPA shell with HTTP 200 does not mean the retired page is present. Inspect the final React route. Do not restore Supporter as a rollback side effect.

The runner's scenarios perform navigation, search, menu/detail open/close, filter changes, read-only simulation and export-panel inspection. These intentionally do not create/update/delete application records. Normal sessions/telemetry may be generated by viewing the site; do not promise a zero-write database. Never load the local fixture seeder or call broad cleanup utilities against production.

## Production mutation requires a separate concrete plan

Before any signup, import, save, clone, collection quantity change or other record mutation, obtain authorization for the exact production identity/fixture and operations. Define run ownership, initial-state evidence, tracked IDs, intended mutations, and cleanup that restores initial data or removes only newly authorized fixture records. Explain any irreversible deletion and follow applicable confirmation rules. Scope auth/session changes too; do not ask for credentials in artifacts or store cookies/tokens in reports.

A dedicated fixture's absence blocks mutation checks; it is not authorization to create one or repurpose a customer's account. Run cleanup even after partial failure (imports may create an empty deck before failing). Verify cleanup read-only and report pending work loudly. M1 did **not** prove production mutation rollback/cleanup, authenticated persistence, real Google OAuth, or account credential workflows; require future live verification rather than inheriting local results.

## Failure and completion

Use the failed DOM/screenshot and observed heading before changing a selector. M1's first Collection assertion used “Collection”; inspecting “My Collection” and rechecking empty-owned behavior resolved a harness error. Keep its first failure in the report. If a changed label is product behavior, compare against the intended contract rather than accepting it automatically.

After a post-release failure, prominently alert Kyle with the scenario, confirmed deployed SHA, user-visible impact if known, and evidence. Offer a scoped corrective rollback through Ship, retaining shelved Supporter; do not automatically revert a whole milestone. Missing browser access is a validation gap and cannot be replaced by health success.

Live M1 production evidence supports Guest desktop Home/menu, catalog search/detail/art, one public read-only deck's draw/redraw/export, empty browser-local collection, retired route/API absence, and no captured browser errors. It does not establish production mobile, light theme, authenticated account/collection/deck writes, foil Apply, empty-search behavior, real OAuth, service-client access, independent modules or host integration. The newly extracted reusable runner has local validation; its packaging itself has not been run against production. Use the [M1 report](../../../../docs/evidence/frontend-preparation/m1/verification.json) as historical evidence and report the current selected run separately.
