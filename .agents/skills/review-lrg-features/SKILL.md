# Review LRG features for Excelsior

Maintain intentional feature parity between the four LRG repositories and the Excelsior monorepo. Discovery is read-only except for private review metadata. A review, a schedule, or a broad parity request never authorizes a feature port.

1. Read Excelsior's current root/scoped instructions and inherited global rules. Preserve local changes. Verify the active GitHub login is exactly **KyleGowen** before reading the private BMG repositories; prefer the connected GitHub tools and verify access to each repository. CLI credentials are separate. If identity is wrong or unavailable, ask Kyle to authenticate his personal account; never switch accounts, print tokens, or change global Git configuration. Continue independently accessible sources when a single repository is unavailable, but report incomplete coverage.
2. Read [the review procedure](references/reviewing-changes.md). Resolve exact release/tag and commit evidence for `BMG-Associates/database-api`, `database-ui`, `deckbuilder-ui`, and `auth-ui`, plus Excelsior's current default branch and relevant local changes. Read each source's instructions, provenance, and prior review decisions. Distinguish published release, merged-but-unreleased, unmerged branch, local-only, and deployed state. Missing releases do not mean no changes; label a default-branch comparison **unreleased**. Do not present local work or a package version as a published release.
3. Group each feature or fix with its prerequisites, follow-up fixes, and tests. Reconstruct the Excelsior origin for each affected file/behavior, then compare the LRG-specific change with current Excelsior behavior. Omit unchanged forward ports and behavior already present or superseded in Excelsior. An LRG fix to Excelsior-derived code can still be a new candidate: compare the incremental fix instead of excluding its entire ancestry. Follow shared dependencies, renamed files, indirect provenance through another BMG repo, and independently implemented equivalents. Keep uncertain lineage explicit.
4. Use the ignored private directory `.local/lrg-port-review/` for review state, append-only decisions, and reports; verify it is ignored before writing. Read existing state first, retain stable feature IDs and exact source revisions, and distinguish review checkpoints from adoption. Never commit private review evidence, raw private source/PR text, or release payloads. **User data is not a feature**: do not access or copy production records, accounts, saved decks, collections, telemetry, backups, credentials, or correspondence. Review code/schema changes with sanitized descriptions and fictional fixtures only. Repository access does not establish ownership or redistribution rights; surface known reuse constraints without inventing them.
5. Return one numbered row per independently approvable feature/fix, with a stable ID, source repo(s) and release/ref, concise before/after behavior, novel LRG contribution and origin evidence, Excelsior destination, adopt/adapt/defer recommendation, dependencies/risks, focused checks, and **Awaiting Kyle's approval**. Consolidate the same novel fix duplicated across LRG repos into one row with all evidence. Do not bundle unrelated features into an approval. Summarize excluded categories and already-present counts separately; never pad the approval list with them. State coverage gaps and the selected source revisions. **Stop after the table.**
6. Honor approve/discard/defer/reopen decisions only from Kyle and only for the identified review rows and source revisions. Keep discarded features retrievable on request and suppressed from later candidate tables until he explicitly reopens them; new titles or commit hashes do not reset a discard. After an explicit feature selection, adapt only the selected behavior to Excelsior under its own instructions and verification gates. Recheck the source and destination; material changes require a revised review. Record adoption only after actual implementation and verification. Approval does not authorize commits, pushes, deployment, paid provisioning, source-repository writes, or changes to user data.

Use Excelsior's backend and `frontend/` architecture, native account/session behavior, user-data preservation, full catalog/legacy support, artwork rules, and release gates. Do not import standalone BMG hosts, branding, disabled guest-only features, confidential service wrappers, infrastructure selectors, or migration numbering merely to match repository structure. Feature parity can require a different implementation.

## Post-Run Learning

Report a compact useful finding about missed dependencies, origin tracking, equivalent behavior, or review coverage. Private operational state belongs only in `.local/lrg-port-review/`. Propose a sanitized improvement in the run report; change the owning skill or governance only through an explicitly requested reviewed update. Do not copy private LRG material into AgentOS or public Excelsior artifacts.
